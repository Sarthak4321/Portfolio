Methodology

Engineering Philosophy

01
Start with the problem
Before choosing a framework or database, I seek to understand the actual problem. Who is using the system? What data needs to exist? What can go wrong? What needs to happen concurrently? Good engineering starts with asking the right questions rather than immediately writing code.
02
Design before complexity
I prefer clean architectures, but I don't believe every project needs unnecessary layers. The goal is to find the simplest architectural design that can reliably solve the problem today while leaving enough room to scale cleanly tomorrow.
03
Think about failure
A successful request is only one part of a system. I focus on failure cases: concurrent requests race conditions, query bottlenecks, API timeouts, and token compromise. This mindset guides transaction handling and authentication boundaries.
04
Build for production
I enjoy the engineering work that follows the core feature implementation: performance tuning, security checks, Docker environments configuration, and monitoring setups. These are key blocks of stable products.

Case Studies & Experience

EvntMet
MARKETPLACE SYSTEM

Transactional Safety at Scale

EvntMet is an end-to-end marketplace application. I approached it as a system with distinct responsibilities: role-based dashboards, booking engines, media assets stored via Cloudflare R2, and database models managed on PostgreSQL.

The core architectural highlight was implementing transactional row locking to isolate concurrent booking operations and prevent double-booking conditions, ensuring absolute database consistency.
